¿Qué son los Anti-Patrones?

Los anti-patrones son soluciones recurrentes que parecen convenientes a corto plazo, pero aumentan la carga cognitiva, ocultan dependencias y complican el mantenimiento del código a futuro.

💡 Objetivo del Módulo

Identificar y corregir los 5 anti-patrones más comunes en Python para escribir código limpio, profesional y mantenible.

1
from module import *
Contaminación del namespace global.
2
Inconsistencia en Nombres
Violaciones a las normas de estilo PEP8.
3
__init__.py Sobrecargados
Lógica de negocio innecesaria en paquetes.
4
Imports Anidados Extensos
Acoplamiento rígido e imports circulares.
5
Desorden en Declaraciones
Mezclar dependencias sin seguir bloques PEP8.
2. Anti-Patrón 1: Importación Masiva (from module import *)
</> 4Geeks academy

El Problema de import *

Importar todo el contenido de un módulo contamina el namespace global, oculta la procedencia de las funciones y genera colisiones accidentales de nombres si dos módulos exportan la misma función.

❌ Anti-Patrón

Aumenta la carga cognitiva y hace imposible rastrear de dónde proviene cada función.

✅ Solución

Usar siempre Imports Explícitos mencionando únicamente los símbolos necesarios.

❌ INCORRECTO (Importación Masiva)
Anti-Patrón
# ❌ Ambiguo y contamina el namespace
from math import *
from os import *

# ¿De dónde provienen sqrt() o log()?
result = sqrt(16) + log(10)
✅ CORRECTO (Imports Explícitos)
Solución
# ✅ Imports explícitos y trazables
from math import sqrt, log

result = sqrt(16) + log(10)
3. Anti-Patrón 2: Inconsistencia en Nombres (Violación de PEP8)
</> 4Geeks academy

Normas de Estilo PEP8

Mezclar estilos (camelCase, snake_case, PascalCase) confunde a los integrantes del equipo y rompe las convenciones de Python.

snake_case
Variables y Funciones
calculate_total_price(), user_id
PascalCase
Clases
UserProfile, AuthService
UPPER_CASE
Constantes
MAX_CONNECTIONS, API_KEY
❌ INCORRECTO (Mezcla de Estilos)
Anti-Patrón
class user_profile:  # Debe ser PascalCase
    def CalculateTotal(self, ItemPrice):  # Debe ser snake_case
        MaxLimit = 100  # Debe ser UPPER_SNAKE_CASE
        return ItemPrice * 1.16
✅ CORRECTO (Estándar PEP8)
Solución
class UserProfile:
    MAX_LIMIT = 100

    def calculate_total(self, item_price: float) -> float:
        return item_price * 1.16
4. Anti-Patrón 3: Archivos __init__.py Sobrecargados
</> 4Geeks academy

El Propósito de __init__.py

Incluir lógica de negocio o funciones pesadas dentro de __init__.py distorsiona el propósito del paquete y provoca ejecuciones secundarias no deseadas al importar cualquier componente.

✅ Solución

Mantener __init__.py minimalista, usándolo únicamente para inicializar el paquete o re-exportar componentes públicos clave.

❌ INCORRECTO: app/services/__init__.py
Anti-Patrón
# ¡Lógica pesada e infraestructura dentro de __init__.py!
import sqlite3

def get_db():
    return sqlite3.connect("db.sqlite")

class UserService: ...
✅ CORRECTO: app/services/__init__.py
Solución
# Re-exportar únicamente interfaces públicas
from .user_service import UserService
from .auth_service import AuthService
5. Anti-Patrón 4: Imports Profundamente Anidados
</> 4Geeks academy

Acoplamiento Rígido en Rutas

Rutas extensas de importación (from a.b.c.d.e import f) generan un acoplamiento frágil a la estructura de carpetas y facilitan la aparición de errores por imports circulares.

✅ Solución

Aplanar la estructura del paquete y exponer interfaces limpias desde los niveles superiores del módulo.

❌ INCORRECTO (Ruta Extensa)
Anti-Patrón
# Acoplamiento rígido a carpetas internas
from app.api.v1.endpoints.users.services.helpers.formatters import format_name

user = format_name("Juan")
✅ CORRECTO (Interfaz Aplanada)
Solución
# Ruta aplanada y mantenible
from app.services import format_name

user = format_name("Juan")
6. Anti-Patrón 5: Desorden en Declaraciones de Imports
</> 4Geeks academy

El Orden de Imports según PEP8

Imports dispersos dificultan identificar rápidamente las dependencias externas frente a los módulos locales del proyecto.

Bloque 1
Librería Estándar de Python
import os, sys, typing
Bloque 2
Librerías de Terceros (pip)
from fastapi import FastAPI
Bloque 3
Módulos Locales del Proyecto
from app.core import config
❌ INCORRECTO (Mezclado y Desordenado)
Anti-Patrón
from app.core import config
import os
from fastapi import FastAPI
import sys
from app.services import UserService
✅ CORRECTO (3 Bloques PEP8)
Solución
# 1. Librería Estándar
import os
import sys

# 2. Librerías de Terceros
from fastapi import FastAPI
from pydantic import BaseModel

# 3. Módulos Locales
from app.core import config
from app.services import UserService

🧩 ¿Qué es la Arquitectura de Software Backend?

Antes de escribir código o crear archivos, necesitamos un plano estructural que ordene nuestro sistema.

🏗️ ¿Qué es?

Es el plano estructural de alto nivel y el conjunto de reglas que definen cómo se dividen, organizan y comunican las piezas del software.

⚙️ ¿Para qué se usa?

Para separar responsabilidades de forma limpia (interfaz, lógica y datos), trabajar en equipo sin pisarse y facilitar el mantenimiento.

🛡️ ¿Por qué es importante?

Evita el "código espagueti", reduce errores al crecer el proyecto y permite escalar el sistema sin rehacerlo desde cero.

🚀 Las 3 Arquitecturas Backend que Analizaremos a Continuación:
1. MVC
Modelo-Vista-Controlador
2. Por Capas
Layered / N-Tier Architecture
3. Serverless
Arquitectura Sin Servidor
Arquitecturas Backend: MVC
</> 4Geeks academy

1. MVC (Modelo-Vista-Controlador): El Equipo Directo

💡 Para entender la diferencia entre estas tres arquitecturas, imaginemos cómo funciona un negocio de comida.
MVC se enfoca en cómo interactúa el usuario con una pantalla o interfaz.

🎨 La Vista (El Plato servido)

Es lo visual, lo que el comensal ve y toca (botones, formularios, colores).

🧑‍🍳 El Controlador (El Mesero)

Escucha lo que pide el usuario ("quiero una hamburguesa"), va a buscar lo necesario y coordina la respuesta.

📖 El Modelo (La Receta y la Despensa)

Contiene las reglas y los datos puros (cuánta carne lleva, consultar si hay queso en la nevera).

🔑 Idea clave: Separa lo que se ve de lo que se hace y los datos.
Arquitecturas Backend: Por Capas
</> 4Geeks academy

2. Arquitectura por Capas (Layered Architecture): El Edificio Corporativo

🏢 Se enfoca en la jerarquía y el orden del flujo interno del sistema (de arriba hacia abajo). Cada piso solo habla con el piso de abajo.

🖥️ Capa de Presentación (Recepción)

Recibe la solicitud del exterior (peticiones HTTP, APIs, formularios) y entrega la respuesta final.

⚙️ Capa de Negocio (Oficinas de Lógica)

Aplica las reglas importantes del sistema (validar pagos, autorizaciones, reglas y cálculos).

🗄️ Capa de Datos (Archivo / Bodega)

Es el único componente que tiene la llave para hablar directamente con la base de datos o almacenamiento.

🔑 Idea clave: Orden estricto. Si necesitas cambiar la base de datos, solo tocas la bodega sin alterar las oficinas de arriba.

3. Serverless (Sin Servidor): Chefs por Encargo (Bajo Demanda)

⚡ El enfoque cambia por completo: ya no es sobre cómo organizas el código, sino dónde y cómo se ejecuta físicamente la infraestructura en la nube.

👨‍🍳 Chef a Domicilio

En lugar de pagar un restaurante 24/7, contratas a un chef que aparece 3 segundos, cocina cuando entra un pedido, cobra por ese tiempo y se va.

🚀 Cómputo por Eventos

📊 Criterios y Matriz de Decisión para Elegir Arquitectura

Para elegir la arquitectura adecuada, evalúa el proyecto a través de cuatro variables clave: fase del producto, patrón de tráfico, complejidad del dominio y capacidad del equipo.

1. Matriz de Decisión Rápida

Criterio MVC Arquitectura por Capas (N-Tier) Serverless (FaaS / BaaS)
Tipo de Proyecto Monolitos web tradicionales, CRUDs rápidos, paneles admin. APIs empresariales, sistemas con reglas de negocio complejas. Tareas asíncronas, webhooks, MVPs con tráfico impredecible o en picos.
Volumen de Tráfico Constante / Predecible. Alto y constante; requiere escalabilidad horizontal de servidores. Cero tráfico base o picos extremos y esporádicos.
Tiempo al Mercado (TTM) Muy rápido (frameworks todo-en-uno). Medio (requiere definir contratos e interfaces entre capas). Rápido para prototipos; medio a largo si la orquestación crece.
Costo Operativo Servidor fijo (VPS o contenedor básico). Costo fijo medio/alto (infraestructura dedicada y balanceadores). $0 si no hay tráfico; costoso si el volumen de cómputo es alto y sostenido 24/7.
Riesgo Principal Acoplamiento excesivo conforme crece el código ("código espagueti"). Sobre-ingeniería innecesaria en proyectos pequeños. Cold starts (latencia en frío) y dependencia del proveedor (vendor lock-in).
Guía por Escenarios & Regla de Oro
</> 4Geeks academy

2. Guía de Selección según el Escenario

🎯 Elige MVC si:
  • Estás construyendo una aplicación web monolítica donde el backend renderiza las vistas directamente o sirve un cliente web estrechamente acoplado.
  • El equipo busca velocidad de entrega sin diseñar contratos de API complejos desde el primer día.
🏢 Elige Capas si:
  • El sistema maneja reglas de negocio densas, múltiples integraciones externas o prevés cambiar la capa de datos en el futuro.
  • La interfaz (móvil, web, CLI) debe desacoplarse por completo de la lógica del servidor a través de contratos claros (APIs REST, GraphQL).
⚡ Elige Serverless si:
  • La carga de trabajo está basada en eventos (procesamiento de imágenes, envío de notificaciones, webhooks).
  • Es un MVP donde no quieres pagar servidores ociosos mientras validas la idea en el mercado.
  • No quieres gestionar parches de seguridad, sistemas operativos ni escalado de servidores.
👑 Regla de Oro Práctica

No son mutuamente excluyentes: Puedes implementar un backend con Arquitectura por Capas y empaquetar cada caso de uso dentro de funciones Serverless, o usar MVC internamente dentro de una capa de presentación.

Comienza con la solución más simple que cumpla los requisitos del primer trimestre de vida del proyecto; la arquitectura debe evolucionar junto con la complejidad real del sistema, no con la anticipada.

Concepto Clave: Decoradores en Python
</> 4Geeks academy

🎀 ¿Qué es un Decorador en Python?

Un decorador en Python es una función que recibe otra función como argumento, le añade una funcionalidad extra (la "envuelve") y devuelve la función modificada, sin alterar su código original.
Se utiliza con la sintaxis @nombre_del_decorador justo encima de la función que deseas extender.

💡 Analogía: La Persona y sus Accesorios

Imagina que una función es una persona que sabe hacer un trabajo específico: Sabe correr (hace su tarea principal), pero si sale a la calle sin nada más, pasa frío o no tiene permisos para entrar a ciertos lugares.

🧥 Abrigo de Invierno

Revisa la temperatura antes de salir; si hace frío, lo abriga (añade una validación previa).

🆔 Carné de Seguridad (@login_required)

El guardia en la puerta revisa el carné antes de dejarlo pasar a la sala (autenticación/permisos).

⏱️ Cronómetro (@medir_tiempo)

Empieza a contar cuando empieza a correr y registra el tiempo exacto al terminar (monitoreo).

✨ La magia de Python: Poner @abrigo encima de correr() es simplemente vestir a la persona antes de que salga a hacer su trabajo, sin tener que modificar sus músculos ni su cuerpo (el código interno).
19. Decoradores HTTP en FastAPI
</> 4Geeks academy

Decoradores HTTP en FastAPI

En FastAPI, los decoradores HTTP transforman funciones normales de Python en endpoints de una API, vinculando una ruta URL específica y un verbo HTTP con la función manejadora correspondiente.

@app.get()
Lectura
Obtener o consultar recursos.
@app.post()
Creación
Enviar datos para crear nuevos recursos.
@app.put()
Actualización
Reemplazar un recurso existente.
@app.delete()
Eliminación
Borrar un recurso del servidor.
main.py
Python
from fastapi import FastAPI

app = FastAPI()

@app.get("/")
def read_root():
    return {"message": "Hello, FastAPI!"}
20. Cómo hacer una Petición GET en FastAPI
</> 4Geeks academy

Petición GET (Lectura)

Las peticiones GET se utilizan para obtener información del servidor. No llevan cuerpo (body) y pueden recibir parámetros de ruta o query strings.

🟢 Status Code 200 OK

Por defecto, FastAPI retorna un código HTTP 200 OK al responder exitosamente peticiones GET.

get_endpoint.py
Python
from fastapi import FastAPI

app = FastAPI()

# GET Simple (Health Check)
@app.get("/health")
def health_check():
    return {"status": "ok", "service": "backend"}

# GET con Path Parameter y Query Parameter
# URL: http://localhost:8000/users/42?limit=10
@app.get("/users/{user_id}")
def get_user_profile(user_id: int, limit: int = 5):
    return {
        "user_id": user_id,
        "limit_results": limit,
        "role": "admin"
    }
21. Cómo hacer una Petición POST en FastAPI
</> 4Geeks academy

Petición POST (Creación)

Las peticiones POST envían datos en el cuerpo (Request Body) para crear nuevos recursos en el servidor.

🔵 Status Code 201 Created

Se debe especificar status_code=201 en el decorador para indicar la creación exitosa de un recurso.

post_endpoint.py
Python
from fastapi import FastAPI
from pydantic import BaseModel, EmailStr

app = FastAPI()

# 1. Definir el esquema del cuerpo con Pydantic
class UserCreate(BaseModel):
    name: str
    email: EmailStr
    age: int

# 2. Endpoint POST especificando status_code=201
@app.post("/users", status_code=201)
def create_user(payload: UserCreate):
    # FastAPI valida automáticamente payload
    return {
        "message": "Usuario creado exitosamente",
        "user": payload
    }
24. Errores Comunes en el Diseño de APIs
</> 4Geeks academy

Anti-Patrones en el Diseño de APIs REST

1
Devolver siempre 200 OK
Retornar 200 OK incluso cuando ocurre un error en el servidor o el recurso no existe. Usa HTTPException(status_code=404).
2
Usar Verbos en las Rutas de Endpoints
Rutas como /getUser o /createUser rompen el estándar REST. Usa sustantivos en plural: GET /users o POST /users.
3
Reinventar la Validación Manualmente
Hacer if "email" not in request: manualmente en lugar de aprovechar la validación nativa de Pydantic.

Punto 1 Rúbrica: Estructura de Carpetas y Módulos

📁 1. Estructura de Carpetas y Módulos

Decisiones de diseño iniciales: cómo organizar los archivos antes de escribir código.

❌ Por Tipo Técnico (Tradicional)

Agrupar todos los controllers/ juntos, todos los models/ juntos y todos los schemas/ juntos.

Problema: Al agregar una nueva función, debes tocar 5 carpetas distintas a la vez.

✅ Por Dominio de Negocio (Modular)

Crear módulos independientes como users/, products/, billing/.

Ventaja: Todo lo referente a un recurso está agrupado en su propio módulo.

🎯 Principio Fundamental: Separación de Responsabilidades (Separation of Concerns)

Cada archivo y módulo debe tener un único motivo para cambiar. Si cambias la interfaz HTTP, no debes romper las reglas de negocio ni la base de datos.

Punto 2 Rúbrica: Organización de Endpoints y Routers
</> 4Geeks academy

🛣️ 2. Organización de Endpoints (APIRouter)

En lugar de amontonar 50 rutas en main.py, FastAPI utiliza APIRouter como "departamentos" organizados.

🏢 APIRouter como Departamentos

Agrupa rutas por recurso o contexto (ej. /auth, /users, /billing) definiendo la jerarquía sin complicar el código.

Parámetros Clave:
• prefix="/users": Define la ruta base.
• tags=["users"]: Categoriza en Swagger UI (/docs).
app/api/v1/endpoints/users.py
Python
from fastapi import APIRouter

# Departamentos independientes con APIRouter
router = APIRouter(
    prefix="/users",
    tags=["users"]
)

@router.get("/")
def get_users():
    return [{"id": 1, "name": "Ana"}]

@router.post("/")
def create_user():
    return {"message": "Usuario creado"}
Punto 3 Rúbrica: Convenciones Estándar en FastAPI
</> 4Geeks academy

📐 3. Convenciones Estándar de la Comunidad FastAPI

Las piezas estándar que todo proyecto profesional de FastAPI incluye para mantener coherencia:

⚙️ core/config.py

Variables de entorno y configuraciones globales centralizadas mediante pydantic-settings.

🗄️ models/

Modelos de persistencia en Base de Datos construidos con ORM (SQLAlchemy o SQLModel).

📋 schemas/

Modelos Pydantic para la validación estricta de entrada y salida de datos en peticiones HTTP.

🧠 services/ o crud/

Lógica pura de negocio, algoritmos y operaciones de consulta a la base de datos independientes de HTTP.

🔌 4. Arquitectura Frontend vs. Backend Desacoplados

El backend funciona como una caja negra que se comunica mediante HTTP/JSON con clientes independientes (React, móvil, etc.).

📦 Repositorios

Polyrepo: Repositorios separados para frontend y backend.
Monorepo: Un solo repositorio pero con carpetas aisladas e independientes.

🌐 Configuración CORS

Mecanismo de seguridad del navegador. Si el frontend (localhost:3000) y el backend (localhost:8000) están en orígenes distintos, se debe habilitar CORSMiddleware.

🔐 Variables de Entorno

Las URLs de las APIs y secretos de conexión NUNCA van hardcodeados en el código fuente; se leen dinámicamente desde archivos .env.

Monolito vs. Microservicios (Arquitectura Desacoplada)
</> 4Geeks academy

⚙️ Monolito vs. Microservicios

🏰 Monolito

Todo el sistema (usuarios, pagos, catálogo, notificaciones) vive dentro de una única base de código y se despliega como una única unidad ejecutable en un mismo servidor.

🧩 Microservicios

El sistema se divide en múltiples servicios pequeños e independientes, cada uno con su propio repositorio, base de datos y despliegue, comunicándose por red (HTTP/REST, gRPC o eventos).

Característica Monolito Microservicios
Despliegue Todo o nada (un cambio pequeño requiere redesplegar toda la app). Independiente (puedes actualizar Pagos sin tocar Usuarios).
Bases de Datos Base de datos centralizada compartida. Base de datos dedicada por servicio (Database-per-service).
Escalabilidad Escalas toda la aplicación completa. Escalas únicamente el microservicio que tiene alta demanda.
Tolerancia a fallos Un error crítico (ej. memory leak) puede tumbar toda la plataforma. Un fallo en un servicio queda aislado; el resto sigue funcionando.
Complejidad Baja en infraestructura; alta en código a largo plazo. Alta en infraestructura y redes; código simple por módulo.
🔪 Analogía Monolito: Navaja Suiza

Es una sola pieza sólida. Si se rompe el destornillador o quieres cambiar las tijeras, tienes que cambiar la navaja completa.

🧰 Analogía Microservicios: Caja de Herramientas

Cada herramienta es independiente; si se rompe el martillo, compras otro sin afectar a los destornilladores ni a las llaves.

⚠️ 5. Riesgos y Puntos de Atención (Sin Orden)

¿Qué sucede cuando no hay arquitectura ni orden? Se genera deuda técnica y cuellos de botella en el equipo:

🔄 Importaciones Circulares

Ocurren cuando dos módulos dependen mutuamente entre sí porque las responsabilidades no están aisladas adecuadamente.

🔀 Conflictos de Git

Si todo el equipo edita el mismo archivo main.py o routes.py, la fusión de ramas (merging) se convierte en un caos.

💧 Fugas de Lógica de Negocio

Poner lógica pesada o consultas DB directo en los routers impide reutilizar código y escribir pruebas unitarias limpias.
