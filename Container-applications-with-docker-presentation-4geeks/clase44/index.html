🐳 ¿Por qué Contenedores? El Problema de "En mi máquina sí funciona"

Aislamiento de Kernel • Namespaces & Cgroups
📌 Concepto Fundamental:

Un Contenedor Docker es un proceso aislado que empaqueta la aplicación con todas sus dependencias (binarios, librerías, runtime). A diferencia de una Máquina Virtual (VM) que emula un sistema operativo completo con Hypervisor, los contenedores comparten el mismo Kernel del SO host, siendo infinitamente más ligeros y rápidos.

🖥️ Máquinas Virtuales (VMs)

Incluyen SO Guest completo + Kernel + App. Consumen Gigabytes de RAM, tardan minutos en arrancar y requieren virtualización de hardware pesada.

⚡ Contenedores Docker

Aíslan procesos usando Linux Namespaces y Cgroups sobre el Kernel host. Pesan pocos Megabytes y arrancan en milisegundos.

💡 Analogía Feynman: Barcos Cargueros Intermodales

Imagina transportar frutas, autos y químicos. Antes de los contenedores, necesitabas un barco diseñado especialmente para cada tipo de carga. Docker creó el Contenedor Estándar de Carga: no importa lo que haya adentro (Python, Node, Go, Postgres), cualquier barco (servidor Linux, Mac, Windows, AWS) puede transportarlo y ejecutarlo sin cambiar de barco.

🖥️ 1.1 ¿Qué es un Sistema Operativo (SO)?

Administrador de Hardware • Software Base
📌 Definición:

Un Sistema Operativo (SO) es el software principal que administra y coordina los recursos de hardware físicos de una computadora (CPU, memoria RAM, disco, dispositivos de E/S) para permitir la ejecución ordenada de aplicaciones y programas de usuario.

💡 Metáfora: El Administrador del Edificio

El Sistema Operativo es como el administrador de un gran edificio de oficinas. Asigna las llaves de cada oficina (memoria), gestiona la electricidad y el agua (CPU y energía) y se asegura de que ningún inquilino (proceso) interrumpa el trabajo de los demás.

⚙️ Componentes Clave del Sistema Operativo:
  • Kernel: El núcleo que interactúa directamente con los recursos del hardware.
  • Espacio de Usuario (User Space): Donde se ejecutan las aplicaciones, herramientas y sistemas de archivos.

💻 1.2 ¿Qué es una Máquina Virtual (VM)?

Hipervisor • Virtualización Pesada
📌 Definición:

Una Máquina Virtual (VM) emula un entorno informático completo (hardware virtualizado) mediante un Hipervisor. Cada VM instala y ejecuta un Sistema Operativo invitado completo (Guest OS) independiente, con su propio kernel y asignación rígida de recursos.

💡 Explicación Feynman: La Casa de Ladrillos Entera

Una VM es como construir una casa de ladrillos entera con sus propios cimientos, cocina y baño, solo para que duerma una persona. Ocupa mucho espacio (Gigabytes de RAM/disco) y tarda mucho tiempo en levantarse (minutos).

# En virtualización tradicional con Vagrant/VirtualBox:
vagrant up # Descarga gigabytes y levanta un SO completo desde cero

🧠 1.3 ¿Qué es el Kernel en un Sistema Operativo?

Núcleo del SO • Puente Hardware-Software
📌 Definición:

Es el corazón del sistema operativo: el puente directo que comunica el hardware físico (CPU, RAM, disco) con el software y las aplicaciones.

⚙️ Responsabilidades Clave:
  • Administración de recursos: Asigna memoria y tiempo de procesador a cada programa.
  • Control de hardware: Traduce las órdenes de las aplicaciones a los controladores (drivers) de los dispositivos.
  • Seguridad y privilegios: Evita que un programa bloquee el sistema o altere la memoria de otros procesos.
💡 Metáfora:

Es el jefe de sala en un restaurante: los clientes (aplicaciones) no pueden entrar a la cocina ni tocar los fogones (hardware); le piden los platos al jefe de sala (llamadas al sistema), quien cocina y sirve de forma ordenada.

🐳 Relevancia en Docker:

A diferencia de una VM (que corre un kernel propio por cada máquina), los contenedores comparten el mismo kernel del anfitrión, logrando arranque instantáneo y uso mínimo de recursos.

🔍 2. Cimientos de Linux: Namespaces (Aislamiento de Vista)

Aislamiento Lógico • PID, NET, MNT, USER
📌 Concepto:

Los Namespaces son una característica del Kernel de Linux que aísla la vista de los recursos del sistema operativo para un proceso o grupo de procesos (redes NET, procesos PID, montajes de disco MNT, usuarios USER). Para el proceso en ejecución, él cree que es el único proceso activo en todo el sistema.

💡 Explicación Feynman: Las Gafas de Cartón Lateral

Imagina un salón de clases lleno de alumnos. Ponerle un Namespace a un niño es ponerle unas gafas de cartón laterales: él solo ve su propio pupitre, cree que el salón está vacío y no puede ver ni molestar a los demás pupitres.

# Crear un namespace de procesos (PID) y montajes aislado manualmente en Linux:
unshare --fork --pid --mount-proc bash

⚖️ 2.1 Cimientos de Linux: Control Groups (cgroups)

Límite de Recursos • RAM, CPU, I/O
📌 Concepto:

Los Control Groups (cgroups) son una funcionalidad del Kernel de Linux que limita, contabiliza y aísla el consumo de recursos físicos de hardware (RAM, núcleos o porcentaje de CPU, ancho de banda de E/S de disco) asignados a un grupo de procesos. Previene que un proceso descontrolado consuma todo el servidor.

💡 Explicación Feynman: Las Reglas Estrictas del Profesor

Si los Namespaces son las gafas de cartón, cgroups es la regla estricta del profesor en el aula: "cada alumno solo tiene permitido comer máximo 2 galletas del paquete y usar 100 MB de plastilina". Evita que un niño comelón (memory leak) se acabe los recursos de toda la clase.

# Limitar un grupo de procesos a 512MB de RAM usando cgroups en Linux:
cgcreate -g memory:mi_grupo && cgset -r memory.max=512M mi_grupo

📦 3. ¿Qué es un Contenedor? (Container)

Proceso Encapsulado • Kernel Compartido
📌 Concepto:

Un contenedor no es una máquina virtual. Es simplemente un proceso regular de Linux encapsulado y restringido mediante namespaces y cgroups. Comparte el mismo kernel del sistema operativo anfitrión sin duplicar hardware ni SO.

💡 Explicación Feynman: El Edificio de Apartamentos

En lugar de construir una casa entera para cada huésped (VM), alquilas un edificio de apartamentos: todos comparten las mismas tuberías de agua y cimientos principales (kernel), pero cada quien tiene su puerta con llave y su propio medidor de luz.

# Inspeccionar que el contenedor es un proceso PID nativo del SO anfitrión:
docker top mi_contenedor # Muestra los PID de Linux ejecutando la app

⚙️ ¿Qué es el Docker Engine?

Motor Central • Cliente-Servidor
📌 Definición:

Es el motor central de Docker: la aplicación cliente-servidor que se instala en el sistema operativo anfitrión para construir, distribuir y ejecutar contenedores.

🧩 Componentes Principales:
  • Servidor (Daemon - dockerd): El proceso que corre en segundo plano gestionando imágenes, redes, volúmenes y el ciclo de vida de los contenedores.
  • API REST: La interfaz de comunicación que recibe órdenes y conecta al cliente con el demonio.
  • Cliente CLI (docker): La herramienta de línea de comandos que usa el desarrollador para enviar instrucciones (e.g., docker run, docker build).
🎼 Metáfora: El Director de Orquesta

Es el director de orquesta en un teatro: Tú como usuario le pasas las partituras por el micrófono (la terminal CLI); el director (la API y el demonio) interpreta las notas y coordina a cada músico (redes, imágenes y procesos del sistema) para que la obra suene en perfecta armonía sin que tú tengas que afinar cada instrumento a mano.

⚡ Relevancia:

Es la capa intermedia que traduce comandos sencillos de usuario en llamadas complejas al kernel de Linux (namespaces y cgroups) para materializar los contenedores.

📜 5. Dockerfile

📌 Concepto:

Es un archivo de texto plano con instrucciones secuenciales que definen el entorno, dependencias, archivos y comandos necesarios para construir una aplicación reproducible.

💡 Explicación Feynman: La Receta de Cocina

Es la receta de cocina escrita en un papel. Dice: toma una base de masa (sistema base), agrégale salsa de tomate (dependencias), pon el queso encima (tu código) y hornea a 180°C (puerto expuesto).

COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
CMD ["python", "main.py"]

🖼️ ¿Qué son las Imágenes de Docker?

Plantillas Inmutables • Solo Lectura
📌 Definición:

Son plantillas binarias empaquetadas, inmutables y de solo lectura que contienen todo lo necesario para ejecutar una aplicación: código, entorno de ejecución (runtime), librerías, variables de entorno y archivos de configuración.

⚙️ Características Clave:
  • Estructura por capas (layers): Cada instrucción del Dockerfile crea una capa reutilizable y cacheable sobre la anterior.
  • Inmutabilidad: Una vez construida, una imagen nunca se modifica; si el código cambia, se compila una nueva versión con un nuevo tag.
  • Portabilidad: Se construyen una sola vez y corren exactamente igual en cualquier máquina que tenga Docker instalado.
💡 Metáfora: La Receta Plastificada / Plano Arquitectónico

Es una receta de cocina impresa y plastificada (o una foto congelada): No puedes comer la receta impresa ni interactuar con ella directamente porque es solo papel estático; pero con esa misma plantilla exacta puedes preparar mil platos de comida idénticos (contenedores) en cualquier cocina del mundo.

⚡ Relevancia:

Son el molde estático del que nacen los contenedores: la imagen es el plano arquitectónico en reposo, mientras que el contenedor es el edificio vivo en construcción y operación.

🐙 8. Docker Compose (`compose`)

📌 Concepto:

Herramienta para definir y ejecutar aplicaciones multi-contenedor mediante un archivo declarativo YAML (docker-compose.yml). Permite levantar con un solo comando la API, la base de datos y la caché en una red interna compartida.

💡 Explicación Feynman: Director de Banda de Garaje

Si un contenedor es un músico solista tocando la guitarra, Docker Compose es el director de una banda pequeña de garaje: le indica al bajista, al baterista y al cantante que empiecen a tocar al mismo tiempo y coordinados.

services:
  backend:
    build: .
    ports: ["8000:8000"]
    environment: [DB_HOST=postgres_db]
  postgres_db:
    image: postgres:15
    environment: [POSTGRES_PASSWORD=secretpassword]

# Comando: docker compose up -d
Clase 44 • Blueprint de la Imagen: El Dockerfile
</> 4Geeks academy

📜 Anatomía de un Dockerfile Optimizado

# 1. Imagen base minimalista
FROM python:3.11-slim

# 2. Directorio de trabajo
WORKDIR /app

# 3. Copiar dependencias (Caché de Capas)
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# 4. Copiar código fuente
COPY . .

# 5. Puerto expuesto y comando de inicio
EXPOSE 8000
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
1. Layer Caching (Caché de Capas)

Docker ejecuta cada línea como una capa inmutable. Si no cambias requirements.txt, el paso de RUN pip install se reutiliza instantáneamente del caché.

2. Selección de Base Image

Prefiere python:3.11-slim sobre python:3.11. Reduce vulnerabilidades de seguridad y tamaño de descarga de 1 GB a 150 MB.

3. CMD vs ENTRYPOINT

CMD define los argumentos por defecto modificables al hacer docker run. ENTRYPOINT fija el binario ejecutable principal.

Clase 44 • Multi-Stage Builds: Imágenes Ultraligeras de Producción
</> 4Geeks academy

✂️ Multi-Stage Builds: De 1.2 GB a 140 MB

📌 El Desafío de Producción:

Para compilar o instalar ciertas librerías necesitas herramientas pesadas (compiladores C, cabeceras gcc, SDKs). Pero para ejecutar la app en producción solo necesitas los artefactos finales. Multi-Stage usa múltiples instrucciones FROM en un solo Dockerfile.

# Etapa 1: Builder (Compiladores y Wheels)
FROM python:3.11 AS builder
WORKDIR /build
COPY requirements.txt .
RUN pip wheel --no-cache-dir -w /wheels -r requirements.txt

# Etapa 2: Runtime Minimalista
FROM python:3.11-slim AS final
WORKDIR /app
COPY --from=builder /wheels /wheels
RUN pip install /wheels/* && rm -rf /wheels
🎯 Beneficio 1: Seguridad Aumentada

Elimina herramientas de compilación e instructivos de desarrollo que los atacantes podrían usar para vulnerar el contenedor.

🚀 Beneficio 2: Despliegues Ultrarápidos

Una imagen reducida de 140 MB se descarga e inicia en clusters de producción en segundos en lugar de minutos.

volumes:
  postgres_data:
1. Un Solo Comando (`docker compose up`)

Levanta toda tu infraestructura (Backend, Frontend, DB, Redis) en una sola red aislada sin instalar nada en tu laptop.

2. DNS Integrado Automático

El servicio web puede resolver el host db automáticamente sin requerir direcciones IP estáticas.

3. Control de Ciclo de Vida

Usa docker compose down para apagar limpiamente todos los procesos o docker compose logs -f para depurar.

Clase 44 • Manejo Seguro de Secretos & Variables de Entorno
</> 4Geeks academy

🔑 Inyección de Secretos y `.env` en Docker

📌 La Regla de 12-Factor App:

Las credenciales (contraseñas de BD, JWT Keys, API Keys de Gemini) NUNCA se escriben dentro del Dockerfile ni se compilan en la imagen. Se inyectan en tiempo de ejecución desde el entorno del host.

❌ Mala Práctica (Fuga de Seguridad)

Escribir ENV DATABASE_URL="postgres://admin:secret123@..." en el Dockerfile.
Cualquiera con acceso al registro o ejecutando docker history <image> leerá tus claves secretas.

✅ Buena Práctica (`.env` local)

Incluir .env en tu .gitignore y .dockerignore.
Cargar el archivo en Docker Compose mediante env_file: .env o pasar variables en la nube (AWS Parameter Store/K8s Secrets).

Clase 44 • Healthchecks & Orquestación Resiliente
</> 4Geeks academy

🩺 Healthchecks y Orden de Inicio Dependiente

services:
  db:
    image: postgres:15-alpine
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U user"]
      interval: 5s
      retries: 5

  api:
    build: .
    depends_on:
      db:
        condition: service_healthy
📌 El Problema de la Carrera de Inicio

El contenedor de la base de datos puede arrancar en 1 segundo, pero su puerto interno tarda 5 segundos en aceptar conexiones. Si tu API arranca de inmediato, fallará la primera conexión.

🛡️ La Solución: `service_healthy`

`depends_on: condition: service_healthy` detiene el arranque de la API hasta que la prueba de salud (`pg_isready`) de Postgres responda con éxito.

Clase 44 • Antipatrones & Buenas Prácticas de Seguridad
</> 4Geeks academy

⚠️ Los 4 Antipatrones Más Comunes en Docker

1. Usar `:latest` como Tag

Fija siempre la versión (ej. python:3.11-slim-bookworm). La etiqueta latest puede romper tu compilación en cualquier momento si la versión upstream cambia.

2. Ejecutar como Usuario `root`

Crea un usuario sin privilegios en el Dockerfile (RUN adduser appuser && USER appuser) para evitar escapes de contenedor con permisos de root.

3. Olvidar el `.dockerignore`

Sin .dockerignore, estarás copiando megabytes de .git, venv, node_modules y archivos .env a la imagen.

4. Contenedores "Monolíticos"

Un contenedor debe ejecutar un solo proceso principal. Separa tu Backend FastAPI, tu Frontend Next.js y tu DB Postgres en contenedores independientes.
