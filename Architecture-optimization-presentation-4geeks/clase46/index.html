⚡ Principios de Caching: De 350ms a 3ms

Redis • HTTP Cache-Control
📌 ¿Qué es Caching?

Es la técnica de almacenar copias temporales de resultados computados o datos leídos de disco en un medio de almacenamiento ultrarrápido en memoria RAM. Evita volver a ejecutar consultas SQL repetitivas o cálculos pesados.

🐢 Sin Caché (Petición Directa a BD)

Cliente -> FastAPI -> SQL Query -> Disco BD -> Formatear JSON -> Cliente.
Tiempo: ~350 ms por petición.

🚀 Con Caché en Memoria (Redis)

Cliente -> FastAPI -> Redis RAM -> Cliente.
Tiempo: ~3 ms (100x más rápido).

💡 Analogía Feynman: El Chef y las Salsas Pre-cocinadas

Imagina que cada vez que alguien pide espaguetis, el chef tuviera que picar los tomates, cosechar el orégano y cocinar la salsa desde cero (Base de datos sin caché). Caching es mantener un tazón de salsa lista en la barra (Redis): simplemente sirves la porción de inmediato en 3 segundos.

💾 In-Memory (`lru_cache`) vs Caching Distribuido (Redis)

🧠 In-Memory (`functools.lru_cache`)

Guarda los datos en la memoria RAM del propio proceso Python.
• Ventajas: Ultra simple, 0 dependencias externas.
• Limitación: No se comparte entre múltiples réplicas o trabajadores (workers) de FastAPI.

🔴 Redis (Caché Distribuido Key-Value)

Servicio independiente en memoria con soporte para estructuras complejas (Hash, Sets, Lists) y TTL.
• Ventajas: Compartido por todas las instancias de servidores, persiste tras reinicios y soporta alta disponibilidad.

🌐 HTTP Caching en el Navegador y CDNs

HTTP/1.1 200 OK
Cache-Control: public, max-age=3600, s-maxage=86400
ETag: "w/686897696a7c"

# Petición subsecuente del cliente:
If-None-Match: "w/686897696a7c"

# Respuesta del servidor (0 bytes de payload):
HTTP/1.1 304 Not Modified
1. `max-age` vs `s-maxage`

max-age le indica al navegador cuántos segundos guardar el recurso. s-maxage aplica para proxies y CDNs intermedios.

2. Validación con ETag (304 Not Modified)

Si el contenido no ha cambiado, el servidor responde con status 304 sin enviar el cuerpo de la respuesta, ahorrando ancho de banda.

Clase 46 • Patrón Cache-Aside & Time-To-Live (TTL)
</> 4Geeks academy

🔄 El Flujo del Patrón Cache-Aside

1. Cliente solicita GET /inventario/123
2. Backend consulta a Redis: GET item:123
  ├─ Si existe (CACHE HIT): Retorna JSON directo de Redis (3 ms).
  └─ Si NO existe (CACHE MISS):
      a) Backend lee de PostgreSQL.
      b) Guarda en Redis: SETEX item:123 60 "<json>" (TTL = 60 seg).
      c) Retorna respuesta al cliente.
📌 La Importancia del TTL (Time-To-Live):

Asignar un TTL garantiza que las claves expiren automáticamente en Redis, evitando que la memoria RAM se llene indefinidamente y asegurando la eventual consistencia de los datos.

⚠️ "Hay solo 2 problemas difíciles en CS: Invalidación de Caché y poner nombres"

🚨 El Riesgo de Caché Obsoleto (Stale Cache)

Un usuario actualiza el precio de un producto (`PUT /items/123`). Si no borras la clave `item:123` en Redis, los demás usuarios seguirán viendo el precio viejo hasta que expire el TTL.

✅ Invalidación Basada en Eventos

En operaciones de escritura (`POST`, `PUT`, `DELETE`), ejecuta explícitamente `redis.delete("item:123")` para purgar de inmediato la entrada obsoleta.

🐍 Código Python: Conexión Asíncrona a Redis

import redis.asyncio as aioredis
import json

redis_client = aioredis.from_url("redis://redis_db:6379", decode_responses=True)

@app.get("/products/{product_id}")
async def get_product(product_id: int, db: Session = Depends(get_db)):
  cache_key = f"product:{product_id}"
  cached_data = await redis_client.get(cache_key)
  if cached_data:
    return json.loads(cached_data) # Cache Hit

  product = db.query(Product).get(product_id)
  await redis_client.setex(cache_key, 60, json.dumps(product))
  return product

</> 4Geeks academy

⚠️ Los 3 Peligros de Implementar Caché Incorrecamente

1. Cache Stampede (Thundering Herd)

Cuando expira la clave de una consulta muy popular, miles de peticiones simultáneas van directo a la base de datos a la misma fracción de segundo, colapsando el servidor SQL.

2. Cachear Datos Privados o Sensibles en Cachés Públicas

Enviar cabeceras `Cache-Control: public` en endpoints autenticados provocará que proxies intermedios muestren la información privada de un usuario a otros comensales.

3. Olvidar Política de Evicción en Redis

Si no configuras maxmemory-policy allkeys-lru en Redis, el servidor se quedará sin memoria RAM (OOM) y rechazará escrituras.
